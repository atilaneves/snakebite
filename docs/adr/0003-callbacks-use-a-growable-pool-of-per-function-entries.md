# Callbacks use a growable pool of per-function entries

Host code calls guest functions through function pointers and
delegates: `qsort` comparators, druntime hooks that take a delegate,
and unit-threaded's task pool. Issue #98 raced a fixed 64-slot pool of
compiler-generated entries against libffi closures, in a debug build,
for one signature shape: 748.99 ns for the pool, 787.41 ns for the
libffi closure. The pool won. That first pool supported one signature
only, `extern(D) bool function()`, and issue #9 proposed a registry
record as the delegate context word. Research in
`ai/research-ffi-barrier.md` found that memory which is writable and
executable at the same time is the most platform-fragile part of any
call that crosses the barrier: SELinux, PaX, macOS entitlements, and
systemd's `MemoryDenyWriteExecute` setting can all block it. LuaJIT
and cffi both start from a fixed pool for this reason.

We decide as follows.

1. One generic assembly callback entry serves each pool slot, in the
   same `.S` file as the call stub (ADR-0001). It spills the argument
   registers into a save area, then hands the slot's plan and the
   save area to a handler that re-enters the backend. The plan covers
   every signature shape, including MEMORY class returns through the
   hidden pointer. An entry is position independent: it computes its
   own address and its chunk's trailer address relative to the
   program counter, and embeds no absolute address of any table.
2. A slot is keyed by guest function, never by call, and is never
   released. A guest function pointer maps to its slot for the life
   of the program, within the backend instance that owns the function.
   A guest delegate uses the same per-function slot as its function
   pointer, and keeps its own context word untouched, because the
   host passes that context back on every call.
   Native vtables also use callable entries. An interface entry that must
   adjust `this` is keyed by target and adjustment; the entry owns that
   adjustment, not the call site or the delegate context. The same entry
   mechanism can forward to a host method inherited by a guest class.
3. The pool grows on demand. There is no fixed limit and no
   exhaustion error. The first chunk of entries is a template linked
   into the binary. When every slot in every chunk is taken, the pool
   copies the template's bytes into a new read-write mapping, patches
   the chunk's trailer, and changes the mapping to read-execute.
   Memory is never writable and executable at the same time. If the
   kernel refuses to make the mapping executable, the pool maps one
   anonymous memory file twice instead: a read-write view to fill and
   a read-execute view to keep. If that also fails, the pool throws an
   error that names the reason. Pool use is bounded by the number of
   distinct guest functions that ever cross the barrier, which is
   bounded by program size.

## Considered options

- **Registry record as the delegate context (#9).** Rejected. The
  record's lifetime is unknown, because host code may keep the
  delegate in memory the GC does not scan. A per-function slot has
  no lifetime to track.
- **Per-shape entry pools, generated by `static foreach`.** Rejected.
  A callback's cost comes from re-entering the backend, not from its
  entry. One generic entry loses nothing and covers every shape.
- **A fixed pool with a hard limit.** Rejected. A limit that is large
  enough for every program is a guess, and a program that reaches it
  fails with no way to continue. Growth keeps the fixed pool's
  properties for the common case, since the template chunk serves
  every program that needs no more than one chunk.
- **Memory that is writable and executable at the same time.**
  Rejected. This is the platform-fragile part named in the research
  note above. What is accepted instead is a copy of the template
  chunk that is written first and made executable second, or a
  memory file mapped once to write and once to execute. Neither view
  is ever both writable and executable.
- **libffi closures.** Rejected. Slower in the #98 measurement, and
  an external dependency.

## Consequences

The callback handler, not the entry, classifies arguments. It uses
the same plan machinery as a forward call, in reverse. A backend
puts these native addresses in generated vtables, including destructor
entries. Interface references use native object offsets. Virtual calls
load their target from the receiver's vtable; they do not search class
metadata for an implementation. Druntime owns destructor-chain execution.
A backend
registers every word it stores for a guest function's address, so
the plan can swap that word for the function's pool entry when it
crosses the barrier, and swap a pool entry back for the word when
host code writes it through a `ref` or `out` parameter. Issue #9 is
updated to point here.

## Supersedes

The registry-record design proposed in the comments of #9, and the
fixed 512-entry pool this decision first described.
