# Callbacks use a fixed pool of per-function entries

Host code calls guest functions through function pointers and
delegates: `qsort` comparators, druntime's `_d_aaApply2` for
`foreach` over an associative array (#275), and unit-threaded's task
pool. Issue #98 raced a fixed 64-slot pool of compiler-generated
entries against libffi closures, in a debug build, for one signature
shape: 748.99 ns for the pool, 787.41 ns for the libffi closure. The
pool won. Today the pool supports one signature only,
`extern(D) bool function()`, and issue #9 proposed a registry record
as the delegate context word. Research in `ai/research-ffi-barrier.md`
found that allocating executable memory for closures at run time is
the most platform-fragile part of any call that crosses the barrier:
SELinux, PaX, macOS entitlements, and systemd's
`MemoryDenyWriteExecute` setting can all block it. LuaJIT and cffi
both use a fixed pool for this reason.

We decide as follows.

1. One generic assembly callback entry serves each pool slot, in the
   same `.S` file as the call stub (ADR-0001). It spills the argument
   registers into a save area, then hands the slot's plan and the
   save area to a handler that re-enters the backend. The plan covers
   every signature shape, including MEMORY class returns through the
   hidden pointer.
2. A slot is keyed by guest function, never by call, and is never
   released. A guest function pointer maps to its slot for the life
   of the program. A guest delegate uses the same per-function slot
   as its function pointer, and keeps its own context word untouched,
   because the host passes that context back on every call.
3. The pool has 512 entries, generated at compile time. Exhaustion is
   a hard error whose message states the limit. No executable memory
   is ever allocated at run time. Pool use is bounded by the number
   of distinct guest functions that ever cross the barrier, which is
   bounded by program size.

## Considered options

- **Registry record as the delegate context (#9).** Rejected. The
  record's lifetime is unknown, because host code may keep the
  delegate in memory the GC does not scan. A per-function slot has
  no lifetime to track.
- **Per-shape entry pools, generated by `static foreach`.** Rejected.
  A callback's cost comes from re-entering the backend, not from its
  entry. One generic entry loses nothing and covers every shape.
- **Entries generated at run time.** Rejected. This needs writable,
  executable memory. See the research note cited above.
- **libffi closures.** Rejected. Slower in the #98 measurement, and
  an external dependency.

## Consequences

The callback handler, not the entry, classifies arguments. It uses
the same plan machinery as a forward call, in reverse. Issue #9 is
updated to point here.

## Supersedes

The registry-record design proposed in the comments of #9.
